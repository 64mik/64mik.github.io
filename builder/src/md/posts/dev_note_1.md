        2. 싱글톤이란
    =>
    싱글톤은 프로그램 생애주기 동안 하나의 객체만 존재하며, 무거운 데이터를 집중적으로 다루는 곳에 주로 쓰인다.
    이론은 배웠으나 구현 경험이 없어서 학습 목적으로 직접 구현해 보았다. 싱글톤을 구현하기 위해 기본 생성자를 막고, 
    대입 연산자를 통해 복사되는 것도 막았다. 참조를 통해서 접근하는 getInstance 함수 내부에서
    static을 통해 프로그램 실행 중 한 번만 객체를 만들도록 구현했다.
    <= bold 
        3. 개발
    =>
    외부에서 편하게 로그에 기입할 수 있도록 오퍼레이터 << 오버로딩으로 구현헀다.
    만들다보니 getInstance의 매개변수 로그 레벨을 넘기는건 덮어쓰기가 되어 싱글톤 오염이 될 가능성이 있을 것 같아서 
    이를 방지하기 위해 한 줄 단위로 버퍼를 만들어서 객체 소멸시 작성하는 방식으로 구조 변경이 필요했다. 버퍼는 stringStream을 사용했다.

    버퍼를 << 연산자로 ofstream에 삽입하려면 버퍼 뒤에 .str() 을 해야하는 것 같다.
    만드는 도중에 버퍼가 가득 차면 강제종료 되는 것 아닐까 싶어 찾아보니 stringStream은 자동으로 늘려서 웬만한 크기는 괜찮다고 한다.
    wrapper라는 객체를 만들어서 wrapper가 스트링 스트림에 계속 더하는 기능까지는 만들었는데, ~Wrapper를 언제 호출해야할지 아직 잘 감이 안온다
    Wrapper 소멸자가 한 줄 끝날때마다 호출되어야 하는데 호출이 안되는지 로그가 일자로 이어져서 나오는 버그가 생겼다. 
    -> 출력부에서 줄바꿈 endl을 없애서 생긴 문제라 수정했다.
    원래는 자체적으로 padding이라는 함수를 만들었는데 C++에서 지원하는 setw과 stefill 이라는게 더 좋다길래 아쉽지만 변경했다.
    wrapper를 Logger 클래스의 내부 클래스로 만들었다.
    커밋 메시지 작성할 때, feat refactor 같은걸 정하는 기준은 사용자로, 사용자 입장에서 입출력이 같으면 refactor 달라졌으면 feat(정확히는 추가)라고 한다.
    날짜가 바뀌어도 이미 열린 file_은 이전 날짜 파일에 계속 기록되는 문제확인.
    테스트하다가 깨달은 사실은 << 연산자가 string 자료형만 받도록 되어있어 범용성이 매우 떨어진다는 걸 알게 되었다.
    -> 템플릿 사용으로 수정했다.
    또한 << 연산자가 인라인 함수인데 비하여 너무 많은 책임을 가지고 있어서 버퍼에 값을 더하는 것으로 단순화했다.
    이전에는 wrapper 내부, 외부에서 따로 prefix를 만들었으나, wrapper는 <<로 받은 값을 담은 버퍼만 다루기로 하고 write에서 제어하도록 변경했다.
    LOG_ERROR << "메시지"; 같은 형태로 메크로를 정의하여 외부 파일의 사용성을 늘렸다.
